Laporan RBAC & SSO — Sipenamas v2

Analisis arsitektur auth, role/permission Spatie, dan integrasi SSO UKWMS
Backend: sipenamas_v2_backend · Disusun 2026-09-18
Temuan utama. Pondasi yang diinginkan — Spatie fresh, permission resource-based, SSO UKWMS, tanpa ketergantungan modul groupakses legacy — sudah dibangun dan berjalan. Pekerjaan yang tersisa bersifat decommissioning & hardening, bukan pembangunan ulang.

1. Peta relasi User

User (users) ├─ kodeperson (nullable, unique) ──→ Person.KODEPERSON [anchor read-only, BUKAN FK bisnis] ├─ kodepersonAliases() hasMany ────→ user_kodeperson_aliases [riwayat NIP lama] ├─ Spatie HasRoles ────────────────→ model_has_roles / model_has_permissions ├─ kodeprodi (diisi via job sync) ─→ Prodi.KODEPRODI (lewat homebase_prodi_map crosswalk) └─ actor / target di ImpersonationLog (via kodeperson) Person (person) — 9 relasi bisnis historis (Penelitian, PenelitianTim, KegiatanAbdimas, Insentif, SubsidiApc, HkiPeserta, dst.) └─ TIDAK LAGI dipakai untuk auth — KODEPERSON di tabel bisnis adalah snapshot historis yang tidak boleh di-remap.

Kenapa user_kodeperson_aliases ada: NIP/kodeperson seseorang bisa berubah sepanjang karier. Tabel alias menjaga agar catatan bisnis lama (dimiliki kodeperson lama) tetap terlihat oleh identitas logis yang sama setelah NIP berubah.

2. Arsitektur SSO yang sudah live

  • UkwmsSsoClient → POST ke api.ukwms.ac.id:8100/v1/auth/login (port dari dologinpegawai_curl() legacy).
  • AuthController::login(): user internal lewat SSO; user eksternal (is_external=1) lewat hash lokal Dencoder::encode3t() terhadap paswet.
  • Auto-provisioning: login SSO sukses pertama kali → row User dibuat otomatis (hanya kodeperson, nama, is_external — tanpa role apa pun).
  • SyncUsersFromUwmsdm (Artisan command terjadwal, bukan real-time): sinkron identitas batch dari DB eksternal uwmsdm.
  • MapHomebaseToProdi: membangun crosswalk homebase_prodi_map dari nama satker uwmsdm ke Prodi.NAMAPRODI lokal.
Terverifikasi di kode (AuthController.php baris 52–73): user baru dari SSO dibuat tanpa role, dan login ditolak (403) jika defaultRole() kosong — sistem aktif memblokir user tanpa role, bukan sekadar diam.

3. Arsitektur RBAC yang sudah live

  • Penamaan permission resource-based: "<verb> <resource>" — mis. "approve penelitian", "manage user".
  • PermissionCatalog sebagai single source of truth permission-as-code; PermissionLabelController sengaja hanya edit label/deskripsi — permission set dikunci di kode.
  • 6 role modul bawaan (ADM/PEN/REV/DKN/RKT/AKR) + Super Admin, dilindungi dari penghapusan; role custom bebas dibuat via RoleController.
  • Gate::before beri Super Admin bypass total; dua middleware saja (EnsureRole, EnsurePermission) — tidak ada Policy class sama sekali.
  • Route data digate permission:..., dashboard/menu digate role:... — dipisah sengaja agar role custom tetap dapat akses data walau belum punya dashboard khusus.

5. Tradeoff desain yang sudah diambil

  1. Permission-as-code, role-as-data — aman dari privilege creep liar via UI, tapi setiap kebutuhan permission granular baru = deploy kode, bukan klik admin panel.
  2. Dual gating (role: untuk dashboard, permission: untuk data) — role custom dapat akses API tapi belum tentu dapat menu di frontend, kecuali navigasi frontend juga dibuat permission-aware.
  3. Auto-provisioning saat login SSO pertama — nyaman, tapi eksistensi akun dipercayakan penuh ke apa pun yang dikembalikan SSO (dimitigasi oleh blokir 403 tanpa role).

6. Risiko tersisa & cara penanganan

#RisikoCara penanganan
1 SSO jadi single point of failure — user internal tidak punya fallback lokal. Timeout + circuit breaker eksplisit di UkwmsSsoClient; UX error jelas; pertimbangkan jalur break-glass khusus Super Admin (diaudit ketat), bukan fallback password lokal untuk semua user.
2 Dual source of truth selama syncGroupAksesColumns() masih hidup. Logging/alert saat sync gagal; tetapkan tanggal deprecation bersama pemilik aplikasi legacy lain; hapus shim setelah semua pindah.
3 Identity drift — kodeperson berubah, alias tidak sinkron. Jadwalkan AuditPersonUserLinks di scheduler secara periodik, bukan hanya sekali saat migrasi awal.
4 Dead code menambah luas permukaan kode tanpa manfaat. Arsipkan command migrasi satu-kali setelah dikonfirmasi jalan di semua environment; hapus Groupakses/Groupaksesdetail langsung (blast radius nol).
5 guard_name = 'sanctum' hardcoded di seluruh role/permission. Bukan urgent selama API-only, tapi dokumentasikan sebagai batasan desain agar tidak jadi kejutan bila nanti butuh guard web.

Kesimpulan

Tidak perlu "merombak" apa pun — arsitektur RBAC + SSO yang diinginkan sudah berdiri dan berjalan dengan benar, termasuk dua titik yang sempat diragukan (default role user baru, dan timestamp audit impersonasi) — keduanya sudah diverifikasi langsung di kode dan terbukti aman. Fokus selanjutnya: decommissioning titik sambungan lama-baru yang sengaja dipertahankan untuk kompatibilitas.
